  **2026-09-29, second session — (4) investigated, fix shipped as D-046 — since refuted, see below.** Confirmed from PostgREST's own docs and multiple `supabase/supabase` / `PostgREST/postgrest` GitHub issues (sourced, not guessed) that PostgREST's schema-cache introspection only lists a relation when a configured role (`anon`/`authenticated`) holds _some_ privilege on it — zero grants for those roles produces exactly PGRST205 ("could not find the table in the schema cache"), not a 42501 permission error. So this was never purely a caching/NOTIFY problem; it's consistent with `public_profiles` genuinely having no grant for those roles on the real Branching-managed DB. `public_profiles` (the view) never got an explicit `grant select` anywhere in the migrations — it only ever relied on `20260928000000_grants.sql`'s `alter default privileges for role postgres in schema public grant select, insert, update, delete on tables to anon, authenticated`. Per Postgres docs, `ON TABLES` in `ALTER DEFAULT PRIVILEGES` does cover views created afterward, but strictly only for objects created by the exact role named (`postgres`) — not inherited, not role-membership-based. On a project we don't fully control the migration-application role for (Supabase Branching), relying on that role match for one specific relation is fragile; `countries`, a plain table added in the very same migration file, is confirmed reachable via PostgREST on a live Vercel preview (PR #15's Playwright run) while the view is not — consistent with a role-matching or view-specific gap on that one object, though this sandbox cannot directly confirm which. **Fix shipped**: `supabase/migrations/20260929030000_public_profiles_explicit_grant.sql` — an explicit, unconditional `grant select on public.public_profiles to anon, authenticated;` plus a re-sent `notify pgrst, 'reload schema';`, removing the dependency on default-privilege inheritance entirely. Pushed directly to `origin/sprint-1` (`checks`/`migrations`/`pgtap` CI jobs trigger on push; `e2e` triggers on the resulting Vercel `deployment_status`, same as any push) — **not yet confirmed working**, since this sandbox has no way to read back the CI/Vercel result (no `gh` CLI installed, no GitHub API token — `curl` to the REST API 404s unauthenticated, confirming the repo is private).
