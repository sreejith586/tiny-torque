- **MV-S1-07 blocked: PostgREST never cached `public_profiles`, breaking every `/u/{handle}` request (PGRST205), and a migration-based `NOTIFY` didn't fix it — needs Sreejith's action.** Full story: `public_profiles` (identity_v2.sql, weeks-old) had never been queried through PostgREST before this task (handle-availability checks run client-side against an authenticated session that — turns out — never actually got exercised against a real anon-facing SSR path either; pgTAP bypasses PostgREST entirely, connecting straight to Postgres). The new `/u/[handle]` page is the first-ever fully-anonymous SSR read in this app, and it surfaced that PostgREST's schema cache is stale: every request 500s with `Could not find the table 'public.public_profiles' in the schema cache`. Added `supabase/migrations/20260929020000_reload_postgrest_schema.sql` (`notify pgrst, 'reload schema';` — the standard Supabase fix, normally sent automatically by `supabase db push` but apparently not by Branching's own migration sync). **Confirmed via two separate diagnostic Playwright round-trips that this did not clear the cache** — identical PGRST205 both before and after the migration applied. **Sreejith then restarted the database — same result again**, and (suspiciously) the exact same Vercel error digest (`1784047441@E394`) came back, which reads more like the same underlying condition recurring than a fresh failure. **Ruled out 2026-09-29:** PR #17 merged to `staging`; Sreejith separately restarted `staging`'s own Supabase instance. Re-ran the Playwright job against `staging` post-restart — **still 500, still the same failure mode** (`/u/no_such_collector_xyz` → 500 instead of 404). This rules out the "restart hit the wrong branch" theory — `staging`'s own DB, freshly restarted, has the identical problem. The issue is not branch-isolation-specific; it's something about how this Supabase project's PostgREST layer is configured or provisioned. Not yet tried at the time: (1) Supabase dashboard → Settings → API → "Reload schema" specifically (a schema-cache reload is a different action from a full database restart — still untested, needs dashboard access this sandbox doesn't have); (2) checking Supabase project logs/status page for a genuinely broken PostgREST instance vs. a caching quirk — also needs dashboard access; (3) querying `public_profiles` directly via `psql`/SQL editor to confirm the view itself is intact — also blocked, this sandbox has no real `DATABASE_URL` and no local psql/Postgres/Docker installed to even dry-run the new migration below (relied on CI's no-Docker `migrations` job instead, plus `guard.sh`/`typecheck`/`lint` all green locally); (4) checking whether PostgREST needs the view to have explicit grants beyond `ALTER DEFAULT PRIVILEGES`.

  **2026-09-29, second session — (4) resolved via research, fix shipped (D-046):** confirmed from PostgREST's own docs and multiple `supabase/supabase` / `PostgREST/postgrest` GitHub issues (sourced, not guessed) that PostgREST's schema-cache introspection only lists a relation when a configured role (`anon`/`authenticated`) holds _some_ privilege on it — zero grants for those roles produces exactly PGRST205 ("could not find the table in the schema cache"), not a 42501 permission error. So this was never purely a caching/NOTIFY problem; it's consistent with `public_profiles` genuinely having no grant for those roles on the real Branching-managed DB. `public_profiles` (the view) never got an explicit `grant select` anywhere in the migrations — it only ever relied on `20260928000000_grants.sql`'s `alter default privileges for role postgres in schema public grant select, insert, update, delete on tables to anon, authenticated`. Per Postgres docs, `ON TABLES` in `ALTER DEFAULT PRIVILEGES` does cover views created afterward, but strictly only for objects created by the exact role named (`postgres`) — not inherited, not role-membership-based. On a project we don't fully control the migration-application role for (Supabase Branching), relying on that role match for one specific relation is fragile; `countries`, a plain table added in the very same migration file, is confirmed reachable via PostgREST on a live Vercel preview (PR #15's Playwright run) while the view is not — consistent with a role-matching or view-specific gap on that one object, though this sandbox cannot directly confirm which. **Fix shipped**: `supabase/migrations/20260929030000_public_profiles_explicit_grant.sql` — an explicit, unconditional `grant select on public.public_profiles to anon, authenticated;` plus a re-sent `notify pgrst, 'reload schema';`, removing the dependency on default-privilege inheritance entirely. Pushed directly to `origin/sprint-1` (`checks`/`migrations`/`pgtap` CI jobs trigger on push; `e2e` triggers on the resulting Vercel `deployment_status`, same as any push) — **not yet confirmed working**, since this sandbox has no way to read back the CI/Vercel result (no `gh` CLI installed, no GitHub API token — `curl` to the REST API 404s unauthenticated, confirming the repo is private). Whoever opens the `sprint-1 → staging` PR (compare: `https://github.com/sreejith586/tiny-torque/compare/staging...sprint-1`) should check that run first via `e2e/smoke.spec.ts`'s `unknown handle 404s (F-14 AC)` test before merging — if it's still 500/PGRST205, the grant theory was wrong and items (1)-(3) above are next.
